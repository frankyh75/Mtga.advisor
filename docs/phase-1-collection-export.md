# Phase 1 Collection Export (Local Logs Only)

## Phase 1 Scope
**IN scope**
- Export a collection snapshot from local MTGA log files only.
- Parse logs to produce a `collection.json` file with per-card ownership counts.
- Support deterministic, explainable output derived solely from logs (no network calls).
- Provide user-facing error messages when logs are missing, incomplete, or outdated.

**OUT of scope**
- Any external data sources (APIs, websites, account sync).
- Meta/deck recommendations, match history, or gameplay analytics.
- Real-time syncing or background log tailing beyond a single export run.
- GUI features beyond a minimal CLI or file output.
- Card metadata enrichment (names, images, set details) beyond IDs.

## Assumptions
**About MTGA logs**
- MTGA writes local logs that include collection-related events or snapshots.
- Log format is semi-stable but may drift; parsing must be defensive.
- Logs are readable without running MTGA, but may be incomplete if MTGA was not recently launched.

**About platform limitations**
- Windows and macOS are expected to provide local log files.
- iOS/Android logs are out of scope (no local log access assumption).
- Path discovery may be OS-specific; unknown platforms should fail with a clear message.
- macOS log path (confirmed): `~/Library/Logs/Wizards of the Coast/MTGA/`.

**About data completeness and freshness**
- Export is only as accurate as the most recent log data available.
- If MTGA has not been launched recently, the collection snapshot may be stale.
- Partial logs may yield partial results; tool must surface uncertainty.

## Input Data
- **Considered log files**
  - MTGA player log(s) (e.g., `Player.log`), including rotated or archived versions when present.
  - Any MTGA log file explicitly documented to contain collection inventory events.
  - macOS Standardpfad: `~/Library/Logs/Wizards of the Coast/MTGA/` (enthält `Player.log` und `Player-prev.log`).
  - Windows LocalLow (Standalone): `%USERPROFILE%/AppData/LocalLow/Wizards Of The Coast/MTGA/` (enthält `Player.log` und `Player-prev.log`).
- **Minimal required records**
  - A collection snapshot event or equivalent record containing card identifiers and owned quantities.
  - If only deltas are present, a complete baseline event is required to avoid reconstruction errors.
- **Ignored input**
  - Match results or event telemetry not required for collection ownership.
  - External files or data sources not generated by MTGA logs.
  - Card metadata (names, images, rarities) unless present in the same collection record.

## Output Data
- **Output files**: `collection.json`, `run-report.json`, `raw-samples/`
- **Shape (`collection.json`)**
  - Top-level object with:
    - `schema` (versioned identifier)
    - `source` (string; e.g., `local-logs`)
    - `cards` (object keyed by Arena-native card IDs)
    - `diagnostics` (completeness, warnings, evidence)
    - Optional `cardsSeenInDecks` and `decks` when no snapshot is available (fallback only)
- **Shape (`run-report.json`)**
  - Contains run timestamps, log file list, output paths, and a diagnostics summary.
- **Card identifier strategy**
  - Use Arena-native card identifiers as they appear in logs.
  - Do not attempt to map to external IDs in Phase 1.
- **Quantities and ownership semantics**
  - Each `cards[cardId]` contains:
    - `owned` (integer, count of owned copies)
    - Optional `notes` field if the value is inferred or partial
  - If a card appears multiple times in logs, the latest complete snapshot is authoritative.
  - If only partial data is available, `owned` may be lower bound and must be flagged.

## UI Sketches (Phase 1)
**JSON-View: Collection/Report**
- **Page goal**: Human-readable view of the exported `collection.json`.
- **Primary content**
  - Read-only JSON viewer with collapsible nodes.
  - Header showing `source` and any snapshot timestamp referenced in diagnostics (if available).
  - Summary counts: total cards tracked, total owned copies, number of unknown/partial entries.
- **Key interactions**
  - Search/filter by card ID.
  - Toggle between raw JSON and formatted view.
  - Copy/export button for the raw JSON payload.

**Warnings/Completeness**
- **Page goal**: Explain export quality and any limitations.
- **Primary content**
  - Status banner: Complete / Partial / Stale / Failed.
  - List of warnings with timestamps (e.g., missing logs, stale snapshot).
  - “What was read” list of log file paths and snapshot time used.
- **Key interactions**
  - Expandable details for each warning (reason, impacted data).
  - Guidance actions (e.g., “Launch MTGA and retry”).

## Phase 1 Data Restrictions
- **No images**: Phase 1 does not include card art, icons, or any other images.
- **No external sources**: Phase 1 does not call external APIs, websites, or third-party data sources.

## Failure Modes
- **Missing logs**
  - Surface: “No MTGA log files found. Launch MTGA and retry.”
  - Export should fail with a non-zero status and no `collection.json` output.
- **Partial logs**
  - Surface: “Log data incomplete; export may be partial.”
  - Export may proceed but must mark uncertainty in output metadata.
- **Format drift**
  - Surface: “Unrecognized log format; parsing rules may be outdated.”
  - Export should fail safely, avoiding silent truncation.
- **Stale data**
  - Surface: “Latest collection snapshot older than X days; results may be stale.”
  - Export may proceed but must warn in output metadata.

## Explainability Requirements
- The tool must explain:
  - Which log files were read.
  - The timestamp of the collection snapshot used.
  - Whether the export is complete, partial, or stale.
  - Any assumptions made due to missing data.
- The tool may say “unknown” for:
  - Cards not present in the latest snapshot.
  - Ownership changes that cannot be derived without deltas or baselines.
  - Any metadata not present in logs (e.g., card names, set codes).

## Non-Goals
- Deck recommendations or deck validation.
- Meta signals, archetype tracking, or win-rate analysis.
- Cross-device sync or cloud backups.
- UI overlays or in-game integration.
- Automatic log repair or inference beyond explicit log records.
